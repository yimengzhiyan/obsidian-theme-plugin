## Variable mapping and priority

Writer: `--theme-reading-width: 640px` on `body:where(.fusion-writer-prototype)` → existing body `--file-line-width: var(--theme-reading-width)` → native Reading/Live Preview/Source readable-line-width consumers.

The option class inside :where contributes zero specificity; the selector is (0,0,1). Style Settings 1.0.9 source emits saved ordinary user variables on `body.css-settings-manager` (0,1,1). At the same body scope, saved user values therefore win independent of those two rules' source order. Baseline width is inherited from :root when neither body recommendation nor saved user value applies.

Default has no override rule. The same rule applies in Light/Dark without changing palettes. No !important, consumer/descendant width selectors, Source normalization or new alias family. Native readable-line-width on/off and responsiveness remain Obsidian's responsibility, per Decision 012.

## Style Settings behavior and UX

Selection is configuration, not a runtime mode. Existing optional Style Settings applies its own classes; Fusion adds no JS, custom DOM mutation, command, timer or behavior. Explicit configuration selection is permitted; automatic/runtime mode switching is not.

Fixed-version [mechanism research](P4_1_PRESET_MECHANISM_RESEARCH.md) supports single-key class-select updates and preservation of other stored values. Actual execution in this Fusion prototype is **NOT RUN** here.

UI text explains: saved values always win; Default keeps them; disabling the plugin uses theme defaults and re-enabling may restore selection. The Content Width description explicitly warns that an unset slider may display metadata default 700 while Writer recommends 640, and resetting removes a saved override. No dynamic effective-value or Custom indicator is promised. Whether users understand this distinction is an acceptance question, not resolved by copy review.
